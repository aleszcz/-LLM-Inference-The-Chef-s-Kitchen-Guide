// 6.1 — MEMORY-AWARE ATTENTION

Attention Kernels 🍳

😤 Vanilla (Standard) Attention MEMORY PROBLEM
⚔️ Enemy: O(S²) HBM round trips

The naive implementation computes Q×Kᵀ scores, dumps them to HBM, reads them back, applies softmax, dumps again, reads again... 6 total HBM transfers, with the intermediate matrices growing quadratically with sequence length.

Step 1: Read Q, K from HBM → on-chip Step 2: Compute Scores → WRITE to HBM ← waste Step 3: READ Scores back from HBM ← waste Step 4: Softmax → WRITE Attn to HBM ← waste Step 5: READ Attn back + Read V ← waste Step 6: Compute output → write to HBM At S=4096: Score matrix = 16.7 MILLION entries per head 😱 Double S → 4× memory (quadratic!)
🍳 CHEF ANALOGY

The chaotic chef walks to the fridge 6 times per dish — storing half-finished sauces there and fetching them back. The bigger the menu (longer sequence), the more sauce he stores, until the fridge literally runs out of space.

⚡ FlashAttention v1 (2022) 32× LESS TRAFFIC
⚔️ Kills: Unnecessary HBM intermediate storage

Never materialize the full S×S matrix in HBM. Instead, tile Q, K, V into small blocks that fit in SRAM and compute everything on-chip. Use online softmax — a running correction technique — so you never need the full matrix at once.

Step 1: Read small TILES of Q, K, V → on-chip SRAM ┌─────────────────────────────────────┐ │ For each tile (i,j): │ │ Compute S(i,j) = Q(i) @ K(j)ᵀ │ ← stays in SRAM │ Online Softmax (running stats) │ ← stays in SRAM │ O(i) += A(i,j) @ V(j) │ ← stays in SRAM └─────────────────────────────────────┘ Step 2: Write ONLY final output O → HBM HBM traffic: O(S²) → O(S·d) ~32× less at S=4096 ✅ Note: more arithmetic, but bottleneck was never arithmetic!
🍳 CHEF ANALOGY

The smart chef works in small batches entirely on his prep counter, using a running notepad to track seasoning adjustments as he goes. He only walks to the fridge twice: once to grab ingredients, once to deliver the finished dish.

🔄
FlashAttention v2 (2023)

Swaps the inner/outer loops — Q blocks outer, K/V blocks inner. Less communication between GPU thread warps. Better occupancy.

Reorders which sous chef does what. Less bumping into each other → 2× faster than v1, same recipe.

Built for H100 specifically. Warp specialization: some threads fetch data while others compute simultaneously. Uses FP8 tensor cores.

Dedicated fetchers AND dedicated cooks working at the same time. Custom kitchen built for this exact recipe.

Even newer, fancier kitchen. 71% of the time the kitchen is actually cooking — not waiting.
// 6.2 — KERNEL FUSION

Kernel Fusion 🔧

🔗 Fusing GPU Operations COMPUTE
⚔️ Kills: HBM round trips between operations

Every time one GPU kernel finishes and the next starts, results get written to HBM then read back. Kernel fusion combines multiple operations into one kernel so intermediate results stay in registers/SRAM.

🍳 CHEF ANALOGY

Instead of running to the fridge between every single step, do multiple cooking steps without leaving the counter. Chop + season + sear all in one uninterrupted motion.

Fused QKV Projection

Compute Q, K, and V in one kernel instead of three separate passes.

Chop all 3 vegetables in one cutting session, not three separate trips to the board.
Fused Softmax + Mask

Apply causal mask and softmax together — avoid write-then-read.

Season AND plate in one motion.
Fused Add + LayerNorm

Residual addition + layer normalization in one kernel.

Stir and taste-adjust simultaneously.
Fused RoPE + Attention

Apply rotary position embeddings inside the attention kernel itself.

Add position seasoning while already cooking the sauce.
// 6.2 — CUDA GRAPHS

CUDA Graphs ⚡

📋 Record Once, Replay Forever LATENCY
⚔️ Kills: CPU↔GPU chatter between kernel launches

During decode, the GPU runs the exact same kernel sequence every step. But without CUDA graphs, the CPU launches each kernel individually — 5–10µs overhead each × hundreds of kernels = hundreds of microseconds of the GPU sitting idle per token.

WITHOUT CUDA graphs: CPU: "do step 1" → wait → "do step 2" → wait → "do step 3" → ... ↑ GPU IDLE ↑ GPU IDLE Hundreds of launches × 5-10µs = ~milliseconds wasted per token WITH CUDA graphs: First run: record everything into a "graph" Every run after: one single command → GPU runs full sequence ✅
🍳 CHEF ANALOGY

The manager used to call each chef individually for every single step of every dish. Now he hands the kitchen a laminated recipe card on day one. Every evening service: one signal — "start dinner" — and the kitchen runs itself without waiting for the manager's approval at each step.

The catch: CUDA graphs are static. Different batch size → need a new card. Serving frameworks keep a small pool of pre-captured graphs for common batch sizes.

// 6.3 — KV CACHE ENGINEERING

KV Cache 🗄️

// WHAT IS THE KV CACHE

Every processed token generates Keys and Values that are saved to avoid recomputation. For a 70B model: 2 × 80 layers × 8 heads × 128 dim × 2 bytes = 32,768 bytes per token. At 4K context: ~128MB per request. With many users, this dominates GPU memory.

🏨 Naive Allocation — The Bad Hotel THE PROBLEM

Pre-allocating contiguous memory for the maximum possible sequence length wastes up to 80% of GPU memory through three failure modes:

Reserved Slots

Memory held for tokens not generated yet. Blocked for everyone else.

Hotel holds 100 rooms for a guest who only checked in — "just in case they need them."
Internal Fragmentation

Sequence ends at 500 tokens but you reserved 2048. 1548 slots wasted forever.

Guest checks out after 3 nights but had 30 nights reserved. Empty rooms, no one else can use them.
External Fragmentation

Gaps between finished requests too small for new ones to fit.

Gaps between guests are 50-room gaps. New guest needs 200. Nobody fits.
📄 PagedAttention SOLUTION
⚔️ Kills: 80% memory waste from fragmentation

Borrowed from OS virtual memory. KV cache split into fixed-size pages (16–32 tokens each). Each request's KV cache is a linked list of pages scattered anywhere in GPU memory — allocated on demand, freed immediately when done.

🍳 CHEF ANALOGY

Instead of reserving a giant block of fridge space per guest upfront, assign small standardized containers on-demand as the meal progresses. When a guest leaves, their containers are immediately available for the next guest. Near-zero waste.

Bonus: Requests sharing the same prefix (same system prompt) can reference the exact same physical pages — stored once, shared by many.

🗜️
KV Cache Quantization

Store KV entries in INT8/FP8 instead of FP16. Model computes in FP16, but storage is half the size. Errors average out across attention. Near-linear speedup to decode.

Store leftovers in smaller containers. Same taste, half the fridge space.
🌀
TurboQuant BUZZ

Random rotations before quantization. Achieves 3.5 bits per entry without quality loss. Uses only sums, no matrix multiply — super fast.

Vacuum-seal the leftovers after restructuring them first. 4.5× smaller than original.
🗑️
Token Eviction / Keyformer

Track attention scores. Delete low-scoring tokens entirely. High scorers (VIPs) stay. Refreshed periodically as generation continues.

Throw out prep containers nobody touches. Only VIP ingredients keep their fridge spot.
🎯
Native Sparse Attention 2025

DeepSeek's approach. Three zones: compressed old tokens, selected high-relevance tokens, sliding window of recent tokens. Trained into model from scratch.

Chef trained from day one to use only 3 organized fridge zones. Not a hack — it's how he learned to cook.
// 6.4 — PROMPT & PREFIX CACHING

Prefix Caching 🗂️

♻️ RadixAttention — The Virtual Memory System for LLMs KV CACHE
⚔️ Kills: Redundant prefill for shared prefixes

When thousands of requests share the same system prompt, you're recomputing the same KV entries millions of times per day. RadixAttention (SGLang) stores KV cache entries in a radix tree keyed by token sequences — shared prefixes stored exactly once.

Without caching: 100 req/s × 2,000 token system prompt = 200,000 redundant tokens/second With RadixAttention: "You are a helpful assistant. Drive to convention center?" ─┐ ├─ shared KV stored ONCE "You are a helpful assistant. Best pizza near me?" ─┘ Only the unique question part needs prefill ✅ Result: ~90% prefill reduction for long system prompts
🍳 CHEF ANALOGY

The smart chef makes base stock once, stores it in labeled containers. Every new dish: grab pre-made stock, skip straight to the unique part of cooking. The filing cabinet (radix tree) knows exactly where every stock variant lives.

📌
Sticky Routing

KV cache only lives on ONE GPU. Route same prefix → same GPU. Same user → same GPU. Otherwise cache misses everywhere.

Same customer always goes to the same restaurant location. Their prep work is already done there.
📐
Order Matters!

Prefix caching only works if stable content comes FIRST. System prompt → examples → history → question. Same order, every time.

Stable ingredients always on the same shelf, same position. Chef finds them instantly. Different position = cache miss.
// 6.5 — SPECULATIVE DECODING

Breaking the Sequential Chain 🚀

// THE CORE INSIGHT

Verifying a sequence of tokens is WAY cheaper than generating them. Generating 5 tokens = 5 sequential forward passes. Verifying 5 tokens = 1 forward pass (parallel, like prefill). This asymmetry is everything.

🎯 Speculative Decoding LATENCY
⚔️ Kills: One token per forward pass constraint
Standard decode: The → quick → brown → fox → jumps (5 passes) Speculative decode pass 1: Draft guesses: fox jumps on a Target verifies: ✅ ✅ ❌ ✗ Accepted: "fox jumps" + resample "over" = 3 tokens, 1 pass Speculative decode pass 2 (worst case): Draft guesses: my lazy dog . Target verifies: ❌ ✗ ✗ ✗ Result: resample "the" = 1 token, 1 pass (same as normal — can't lose!) Average at α=0.8: ~3.4 tokens per target pass ✅
🍳 CHEF ANALOGY

The Apprentice (small draft model) quickly preps a guess for the next 4 courses. The Head Chef (big target model) checks all 4 at once and says yes or no to each. Correct guesses are served immediately. Wrong guesses get redone. Head Chef approves in bulk instead of cooking everything himself.

🌳
Tree-Based Speculation

Instead of one chain of guesses, draft produces a tree of candidates. Target verifies the whole tree in one pass. Longer accepted paths.

Apprentice preps multiple possible next courses. Head Chef picks the longest correct path through the options.
📄
Inference with Reference

Draft tokens come from retrieved documents or cached text. Acceptance rate ~0.95+ when output closely mirrors input (summarization, editing).

Instead of guessing, apprentice reads last week's menu. Head Chef agrees with most of it already.
⚡
Spec-Spec Decoding 2025

Draft model doesn't wait for target to finish. Starts generating next batch optimistically assuming all tokens accepted. Pipeline both models.

Apprentice starts prepping the next course before Head Chef finishes checking the current one. Kitchen never stops moving.
🧠
Multi-Token Prediction

Extra prediction heads built into the main model. No separate draft model. Higher acceptance because drafts come from same weights.

Head Chef trains his own internal intuition to predict what he'll cook next — more accurate than a separate apprentice.
🐍
Medusa EASY WIN

Tiny linear heads added to frozen pretrained model. Train only the heads (hours). No draft model. Near-zero VRAM overhead. Just a flag in vLLM/SGLang.

Sticky notes on the Head Chef's station suggesting what comes next. Cheap to add, doesn't change how he was trained.

✅ Speculative Decoding Works Best

  • Low temperature / deterministic
  • Code generation
  • Factual Q&A
  • Small batch sizes
  • Same-family draft model

❌ Speculative Decoding Hurts

  • High temperature / creative
  • Large batch sizes (GPU already busy)
  • Cross-family draft models
  • Very short outputs
// 6.6 — PARALLEL DECODING

Lookahead & Jacobi Decoding 🔄

🔢 The Deep Insight: Autoregression is Optional LATENCY
// THE MATHEMATICAL TRUTH

Autoregression is one way to describe a joint probability distribution over tokens — not the only way. The same P(A,B,C,D) can be computed in parallel via Jacobi iteration and converge to the mathematically identical result.

Autoregressive (sequential): P(A,B,C,D) = P(A) × P(B|A) × P(C|A,B) × P(D|A,B,C) ↑ one token at a time, left to right Jacobi (parallel): P(A,B,C,D) = P(A|B,C,D) × P(B|A,C,D) × P(C|A,B,D) × P(D|A,B,C) ↑ all positions simultaneously, iterate until converged Both describe the EXACT SAME joint distribution ✅ Autoregression is a CHOICE, not a law.
🍳 CHEF ANALOGY

Instead of cooking dish-by-dish in sequence, the chef plates rough guesses for all dishes simultaneously, then iterates — tasting and adjusting everything in parallel — until the whole meal is consistent and correct. Mathematically proven to reach the same result.

👀 Lookahead Decoding NO EXTRA MODEL
⚔️ Kills: Sequential constraint — zero extra parameters

Maintains a window of W future positions, initialized with guesses. Iterates all positions in parallel using Jacobi. Tokens that converge (stop changing) are accepted and the window slides forward.

Already generated: "The quick" Window W=4, initial guesses: [brown] [dog] [sat] [here] Jacobi iteration 1: [brown] [fox] [jumps] [over] Jacobi iteration 2: [brown] [fox] [jumps] [over] ← converged! Accept "brown fox jumps over", slide window → more tokens ✅ Predictable text ("The capital of France is ___") → 1 iteration Creative text → more iterations No draft model. No extra parameters. No training. Just math.
🍳 CHEF ANALOGY

Chef puts out rough guesses for all 4 next courses at once. Tastes everything simultaneously. Adjusts all in parallel. Repeats until every dish tastes exactly right and nothing changes. No apprentice needed — just the head chef working smarter.
